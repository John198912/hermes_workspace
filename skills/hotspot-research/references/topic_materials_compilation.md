# 话题元素材采集工作流 (Topic Materials Compilation)

> **用途**：当用户需要为某个特定话题（如即将创作的内容、B站深度视频、小红书系列等）准备补充素材时，从现有日/周报档案中"挖掘"相关热点，而非启动新的全量采集。
> **与日报/周报的区别**：日报/周报是"从互联网采集新信号"；话题元素材采集是"从已有报告库中提取相关条目 + 标注关联 + 整合分析"。

---

## 触发条件

当用户请求满足以下任一特征时，使用此工作流：

- "从过去N天的热点中，精选与XXX话题相关的信息"
- "结合近期采集的热点，为XXX话题补充元素材"
- "回顾XXX天的日报，找到关于XXX的强相关条目"
- 明确提到"元素材储备"、"补充素材"、"话题准备"等关键词
- 用户举出具体案例来完善话题论证（如"公司配AI但没人用""Token当KPI员工刷"），需要从报告库验证是否存在

---

## 工作流（5步骤，含补采模式）

### Step 1：定位核心信息 + 确定搜索范围

1. 通过 `session_search` 找到最近相关的 cron 会话（确认已有日报产出）
2. 用 `search_files` 列出目标时间范围内的所有日报文件
3. 读取核心日报（通常是最近一期的日报），提取核心事件
4. 确定搜索关键词（中文+英文混合）

### Step 2：双层搜索——先报告库，后外部补采

**第一层：报告库内搜索**

使用多种方式交叉搜索日报MD文件 + AI HOT JSON原始数据：

1. `search_files` 针对单个目标文件搜索特定英文关键词（如 `psycho`）——逐文件精准命中
2. `execute_code` 批量搜索中文关键词（注意50KB输出截断风险）
3. 搜索AI HOT JSON原始数据（路径 `aihot_daily_YYYY-MM-DD.json`）——这些JSON中包含日报未收录的条目

**⚠️ 中文搜索的已知限制**：
- `search_files` 用 `content` 模式对中文字符+正则组合的跨文件搜索不稳定，窄模式（如单关键词）比宽正则可靠
- `execute_code` 批量读28份报告时 `print()` 输出可能被截断——解决方案：（a）分2批各14份运行，（b）或改用 `file_glob` 限定目标报告+`search_files` 逐文件搜索

**第二层：外部补采（仅当用户提到的案例在报告库中确认不存在时）**

触发条件：用户明确提到具体案例，但经过以下穷举搜索后仍无匹配：
- 28份日报MD文件全文搜索 ✓
- AI HOT JSON原始数据搜索 ✓
- 周报搜索 ✓

补采流程：
1. 告知用户"这N个案例日报中确实没有收录——原因是采集系统同期遗漏"
2. 使用 `mcp_brave_search_brave_web_search` 搜索关键词
3. 用 Jina Reader (`r.jina.ai/{url}`) 提取全文
4. 标注为 "🆕 日报遗漏补采" 并注明替代来源
5. 写入文档时在来源索引表中标注"日报遗漏，补充采集（来源）"

**补采来源优先级**：36氪中文报道（eu.36kr.com）> Financial Times/WSJ > Tom's Hardware/Ars Technica > 其他技术媒体

### Step 3：精选 + 分级 + 关联矩阵

对搜索结果进行三轮筛选：

1. **去重**：同一事件在多份日报中重复出现 → 保留覆盖最完整的一期
2. **分级**：
   - 🔴 P0：与核心话题有直接因果/对比/伏笔关系
   - 🟡 P1：有方法论层/认知层关联
   - ⚪ P2：有数据或背景补充价值
3. **关联矩阵**：每个精选话题标注"与核心话题的关联强度"+"逻辑层级定位"

### Step 4：整合输出（SOUL 四视角 + 关联矩阵）

输出格式见下方模板。核心结构：
- 核心信息摘要表
- N个补充话题（每个含维度表 + SOUL叙事建议 + 受众共鸣点）
- 关联矩阵（ASCII图）
- SOUL 四视角整合分析
- 三平台分发方案
- 素材来源索引

```
topic_excavation/{YYYY-MM-DD}/{topic_slug}/topic_materials.md
```

示例：`topic_excavation/2026-05-30/anthropic-altman-amodei-unemployment/topic_materials.md`

归档位置：`~/hermes_workspace/reports/hotspot/topic_excavation/{YYYY-MM-DD}/{topic_slug}/`

## 每个补充话题的标准维度表

```markdown
### 话题N：[标题]

| 维度 | 详情 |
|------|------|
| **日期** | 原始信息日期（含日报覆盖日期） |
| **来源** | 原始来源 + 日报文件 |
| **核心数据/观点** | 2-3句摘要 |
| **信息完整度** | 100%/80%/60%/30% |
| **与核心话题的关联** | 🔴/🟡/⚪ + 一句话关联逻辑 |
| **SOUL叙事建议** | 反常识钩子一句话 |
| **受众共鸣点** | 受众画像 + 情感触发 |

**详细背景**：(2-3段，展开核心观点和上下文)

**对核心话题的增强**：(1-2段，解释这个话题如何补充/解构/质疑核心事件)
```

## ⚠️ 常见陷阱

1. **不要对每条补充话题做完整的四视角分析**——那太重了。四视角整合放在文档末尾，做整体分析。
2. **补充话题数量以论证强度为准**——典型范围5-10个。按照内容性质分两层：
   - **理性论证层**（5个左右）：数据、方法论、个体行动、机构伏笔、现实对账
   - **荒诞行为层**（3-5个）：决策层荒诞（AI精神病）、成本层荒诞（烧钱失控）、生态层荒诞（一边卖一边撤）、KPI层荒诞（刷Token游戏）、结构层荒诞（AI精英阶级分化）
   分层并非硬性约束——关键在于每种话题必须有独特论证角度。
3. **优先选有时间线逻辑的话题**——有"前兆→核心→验证"的时间线比孤立话题有价值得多。
4. **优先选"荒诞/矛盾性质"的内容**——用户明确偏好自带矛盾的素材（如"裁了人省的钱被AI账单吃完""CEO说AI不会替代你但公司内部在制造AI精英阶级"）。这类素材的叙事张力天然比纯数据强。
5. **每个话题要标注信息完整度**——100%（全文提取）> 80%（多源交叉）> 60%（单源摘要）。补采话题也要标注。
6. **补采话题必须与核心话题有时序关联**——只补充与核心事件在同一报道窗口（±7天）内的遗漏素材，不是无限制扩展。
7. **文档必须归档至 git**——与日报/周报同等对待。
8. **如果用户说"这些在日报里提到过"但搜索不到**：先穷举确认（MD+JSON+周报），再透明告知，最后补采。不要擅自下结论说"日报里没有"——先搜，搜不到再说。
9. **🆕 Feishu DM session 文件写入策略（2026-06-03 两次验证）**：

   **已验证可用的写入方式（按优先级）**：
   1. `write_file` ✅ **首选**— 实测成功写入 22,784 bytes MD文件（2026-06-03 excavation_v2）
   2. `patch(mode='replace')` ✅ **备选**— 走不同审批路径，分段替换可成功（206行文档3次操作完成）
   3. `terminal` heredoc/echo/python3-c ❌ **避免**— 可能被审批机制阻塞，且heredoc中 `&` 字符会触发后台进程检测导致 `exit -1`（非DM审批问题，是terminal工具的前台安全检查）

   **⚠️ terminal heredoc 的 `&` 陷阱**：当 heredoc 内容含 `&` 字符时，`terminal(foreground)` 会拒绝执行（"Foreground command uses '&' backgrounding"）——即使 `&` 在引号字符串内。大段markdown内容几乎必然包含 `&`（如链接中的 `&` 参数、Centaurs & Cyborgs 等），因此 **不要用 heredoc 写大型MD文件**。直接用 `write_file`。
