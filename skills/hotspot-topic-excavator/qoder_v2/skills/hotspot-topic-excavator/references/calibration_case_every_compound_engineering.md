## 案例：Every 复利工程上游口径误读（2026-07-05）

**陷阱类型**：事实校准（"二手转述 vs 一手原文"误判——上游客情没校准就直接消费的典型案例）

### 原始陷阱（三层叠加）

**0701 daily 报告（上游）**对 Every 复利工程的描述：
> "1 人管 5 产品 / 80% 时间在 Plan+Review 而非 Coding / 每次解决方案写入 CLAUDE.md 供 AI 后续复用"

**实际 Every 一手原文**（chain-of-thought 2025-12 主文 + resources/compound-engineering.md 2026-05 升级版）：

| 维度 | 0701 daily 口径 | 实际原文 | 偏差性质 |
|------|----------------|----------|----------|
| 关键数字 | "80% 时间在 Plan+Review **而非 Coding**" | "Plan and review steps should comprise **80 percent of an engineer's time**, and work and compound the other 20 percent. In other words, most thinking happens before and after the code gets written." | ⚠️ **失真**——上游把 "and work + compound = 20%" 改写成 "而非 coding"，把"复合步骤"偷换为"逃避写代码"，定性完全改变 |
| 步数演化 | "Plan→Work→Review→Compound"（4 步） | v1 (2025-12) 是 4 步，**v2 (2026-05) 已升级到 7 步**（Ideate → Brainstorm → Plan → Work → Review → Polish → Compound），agent 数量从 26 升到 40+ | ⚠️ **过期**——上游是 12 月发布的二手转述，原网站 5 月已升级 |
| 产品数量 | "5 款产品" | v1 是 5 款 + Every.to 官网（实为 6 个工程对象）；v2 加入 Proof 是 6 款产品 | ⚠️ **欠完整**——上游漏了官网这个工程对象 |

### 为什么危险（被忽视会怎样）

1. **如果直接以「80% 时间不写代码」为内容钩子** → 受众得到的画面是「这人逃避执行」而非「这人在做高价值判断」——后者才是 SOUL 控制性理念的真正论据
2. **如果以「4 步循环」为产品形态介绍** → 教受众用被淘汰的方法干活（v2 已是 7 步，加入 Polish 等关键步骤）
3. **如果以「5 款产品」为论证** → 弱化"复利工程能扩展到多产品"的论点强度（实际 6 个工程对象 + 持续孵化中）

### 修正动作（5 步）

1. **校准表嵌入 §一开头**——不要等到 §五附录才校准，必须在「三路种子信号」之前亮明「已校准」或「已修正」。本案例具体表格见 SKILL.md Step 1.1 模板。
2. **改写锚点描述**——不是「校正一下」，而是**重写**整段上游摘要，以修订版为锚点展开后续深挖
3. **v1→v2 演化检测**——>30 天未更新的 upstream 必查 v 升级信号；Every 案例是 5 个月间隔，对热点话题来说算快速迭代
4. **跳出"标题党误读"陷阱**——把"不写代码"的形容词重写成"做高价值判断"，避免重复传播上游失真
5. **校准时间预估**——5-15 分钟（远低于写报告的时间，但效果是上游失真不会传染下游）

### 验证信号（如何知道 Step 1.1 完成了）

- ✅ §一第一段有「已校准 / 已修正」小字 + 一行修订版锚点描述
- ✅ 报告中所有数字 / 步数 / 数量都对应到至少 1 个一手原文链接
- ✅ 反方 / 第二来源中至少 1 个也提到 v2（不是 Every 一家之言）——本案例中 `every.to/p/ai-is-ready-organizations-aren-t`、`genaipm.com/wiki/concepts/compound-engineering` 都提到 v2
- ✅ 「信息完整度」标注从 60%（上游）→ ≥90%（深挖后）的提升路径要清晰

### 信息完整度提升路径（本案例实际数据）

| 阶段 | 完整度 | 说明 |
|------|--------|------|
| 0701 daily 上游 | 60% | WebSearch（中文） tip 类 + X 推文摘要 + 一句二手转述 |
| Step 1.1 校准后 | 75% | 数字 / 步数 / 数量已纠偏，但还没联网深挖 |
| Step 2A 深挖 5/5 Every 一手 | 92% | WebFetch 49-62K chars × 4 + GitHub README + 12 篇二次源（含 6 篇反方） |
| 完成报告 | 92% | 含 v1→v2 演化 + 5 维度校准表 + 4 文档产出 + git push |

> 关键：每次完整度提升的"成本"都记录——本案例从 60%→92% 用了约 25 分钟工具调用，时间预算合理。

### 反模式（不要这样做）

- ❌ 「先按上游写，§五校准后再改」——下游内容（抖音脚本、小红书卡片）会基于错误版本先做出半成品
- ❌ 「校准留到最终审稿」——一个章节校准后会推动另一章节的修改，级联效应在 §一锁定最难处理
- ❌ 「只校对数字，不校对版本/产品数」——结构性失真比数字失真影响更深（受众对方法论的整体感知）
- ❌ 「用上游口径作为报告唯一的源头」——上游来源是「发现锚点」用的，不是「事实」用的

### 经验总结（一句话）

> **上游 daily/weekly 报告是「锚点探测器」，不是「事实源」**。在 Step 1.1 把探测器变成校准过的真锚点，整个下游才不会传染失真。
